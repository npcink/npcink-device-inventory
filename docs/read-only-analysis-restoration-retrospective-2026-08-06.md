# 只读分析恢复与组合查询开发复盘（2026-08-06）

## 阶段目标

本阶段不是恢复曾经删除的“分析工作台”，而是在 ADR-003 的收缩结果上，根据真实后台数据重新加入能直接回答管理问题的只读分析：采集是否健康、资料是否完整、哪些设备可能需要更新、资产金额登记到什么程度，以及“指定部门中使用某种显卡的人有哪些”。

最终实现包括管理摘要、组合查询、采集健康、数据完整度、硬件变化、更新候选和资产价值七个视图，并保持以下约束：不新增业务状态、不新增数据表、不在分析页修改资产、不恢复问题处置或身份治理。

架构边界和最终口径见 [`ADR-009`](decisions/ADR-009-restore-read-only-analysis.md)。

## 演进过程

### 1. 从“功能消失”回到产品边界

历史版本曾有更多分析和筛选功能，ADR-003 在首次真实试用前主动删除了未经验证的趋势、价值和可写整改流程。后续真实管理表明，删除方向本身正确，但四项总数不足以支持日常判断。

这次没有直接恢复旧代码，而是重新区分三类能力：

- 可以从现有事实计算、无需写入的能力：恢复。
- 需要新业务状态、角色或闭环的能力：继续排除。
- 需要历史数据但已有观测表支持的能力：采用受约束的只读实现。

这一判断避免了“旧功能曾经存在，所以应全部恢复”的路径依赖。

### 2. 先用真实数据确定口径

后台验收时确认了几个仅从代码无法得到的事实：

- 162 台电脑、170 条未归档资产；浏览器端处理当前规模没有明显性能问题。
- 旧数据仍有 `默认` 部门，因此空值、`未分配` 和 `默认` 都应视为待分配，但分析页不能自动改写历史记录。
- 观测历史目前较浅，很多设备只有一条可用观测；硬件变化必须在最近两次双方都有值时才成立。
- Windows 报告的标称 256 GB 磁盘常约为 238 GB，容量阈值必须保留显示容量容差。
- 显卡名称同时存在厂商前缀、商标字符和型号变体，完全相等匹配不适合日常查询。

因此，本阶段的关键规则来自真实数据反例，而不是界面原型。

### 3. 组合查询从精确相等改为可解释匹配

不同字段之间使用 AND，同一字段的多个值使用 OR。显卡和 CPU 提供两种模式：

- 系列包含：规范化大小写、空格、商标符号，并忽略 NVIDIA、GeForce、Intel、Core 等常见厂商词。
- 精确型号：完成相同规范化后要求完整一致。

这样输入 `4060` 可以找到 RTX 4060 系列，同时仍能在需要时区分具体型号。真实后台中，`4060` 命中 13 台、13 人、6 个部门；限定“开发二部”后命中 4 人，多选“开发部”后按 OR 合计 6 台。

没有开放原始硬件 JSON 的任意字段或正则查询，因为这会制造不可控的性能、安全和口径问题。

### 4. 分析详情从跳转改为原地只读弹窗

最初点击分析结果会切换到电脑设备工作区，导致筛选上下文、分页和滚动位置被打断。最终改为复用共享详情组件，并增加只读模式：

- 分析页隐藏手动记录、设置和其他写入入口。
- 关闭弹窗后保留原查询状态。
- 组合查询支持在当前结果中查看上一台和下一台。
- 资产管理页继续使用同一组件并保留完整写入能力。

这次复用不是简单地把原弹窗放大。真实截图暴露了弹窗过宽、横幅过高、卡片密度低和残值入口不明显等问题，随后统一调整为紧凑的信息层级。

### 5. 把资产金额放回设备上下文

资产价值视图可以查看总体金额，但管理员查看单台设备时也需要立即知道残值。详情首屏因此加入购置日期、采购价、当前残值、已知折价和残值率。

金额口径坚持“缺失不是零”：

- 没有登记采购价或残值时显示“未登记”。
- 缺少任一金额时折价和残值率显示“无法计算”。
- 没有明确购置日期时不使用资产创建时间冒充购置日期。

真实资产 698035 的验收结果为采购价 ¥7,500、残值 ¥7,000、已知折价 ¥500、残值率 93%。

## 技术实现摘要

- 新增管理员只读接口 `GET /npcink-device-inventory/v1/analysis/collection-trends`，固定聚合最近 30 天并补齐空日期。
- 聚合查询使用插件自有观测表、限定时间范围，并随观测列表缓存版本失效。
- 更新候选阈值复用现有设置和完整备份，不新增表。
- 组合查询和大部分分布使用浏览器端索引；当前规模足够，约 1000 台或出现可测性能下降后再评估服务端结构化查询。
- 硬件变化复用分页观测接口，只在进入对应标签时加载全部历史页。
- 分析详情复用共享详情组件，通过 `readOnly` 控制可见能力，不复制第二套设备详情。

## 真实验收中发现并修正的问题

1. 筛选区最初使用四列和跨列布局，视觉节奏不一致；改为稳定三列，并将统计合并到筛选卡底部。
2. 独立“查询说明”卡占用过多空间；改为字段旁提示。
3. 结果表同时展示内存和硬盘两列过宽；合并为“配置”。
4. 移动端虽然声明单列，父级隐式网格仍被表格最小内容宽度撑开；通过 `minmax(0, 1fr)` 约束父级网格解决。
5. 只读详情一度扩到 1040px，真实截图证明信息量不需要该宽度；最终使用 780px，资产管理可写详情保留 840px。
6. Ant Design 弹窗默认顶部 100px，低高度屏幕会使底部越界；改为上下各约 32px，并让正文内部滚动。
7. 财务摘要样式命名最初与设置页已有类名冲突；改为详情专用类名，避免共享 CSS 意外覆盖。

## 本阶段经验

### 先恢复问题能力，不恢复历史实现

历史代码只能说明曾经尝试过什么，不能证明其产品边界、查询语义和界面都正确。应先写出当前真实问题，再决定复用数据、规则或组件的哪一部分。

### 只读不等于低风险

只读分析仍然可能产生错误结论。时间范围、缺失值、容量单位、匹配规范化和历史深度都必须明确；错误的只读结论同样会影响采购和资产处置。

### 后台界面必须用真实密度验收

组件库默认尺寸和空白页面原型无法代表 162 台真实数据。桌面宽度、低高度窗口、390px 移动端、长硬件型号、未登记金额和只有一条历史记录都应进入验收矩阵。

### 共享组件应共享事实，调用方决定权限

设备详情的硬件和财务事实只有一份；分析页与资产管理页的区别是允许的动作。用只读模式控制写入标签比复制组件更安全，也能防止两套详情逐渐产生口径差异。

### 文档要同时记录边界、反例和升级条件

“浏览器端查询”不是永远正确的选择，因此 ADR 同时记录了当前规模依据和约 1000 台后的重新评估条件。规范若没有退出条件，容易从临时方案变成无法讨论的永久约束。

## 验证记录

- 前端 ESLint、TypeScript 和 Vite 生产构建通过。
- 硬件审计固定夹具通过。
- PHP fixtures、PHPCS 和 PHPStan 通过。
- 真实 WordPress 后台完成组合查询、精确匹配、多值 OR、容量条件、详情、连续查看和移动端验收。
- 390px 下无页面横向溢出；1280×720 下弹窗保持在视口内。
- 浏览器控制台无 warning 或 error。
