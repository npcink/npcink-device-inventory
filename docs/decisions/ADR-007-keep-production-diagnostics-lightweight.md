# ADR-007：正式环境保持轻量设备上传诊断

## 状态

已接受，2026-08-05。

## 背景

133 设备采集失败和 32/35 资产串号排查期间，曾考虑在 WordPress 后台增加完整的在线排障或观测面板，用于展示 Agent 命令输出、上传请求、身份计算过程和服务器处理结果。

真实排查表明，两类故障分别发生在不同边界：133 是 Windows PowerShell 5.1 非 UTF-8 输出导致 Agent 丢失中文网卡采集结果；32/35 是旧 v1 → v2 迁移缺少证据连续性保护。完整面板并不能替代对原始硬件事实、Agent 反馈 JSON、身份拥有者和观测历史的分层核对。

该功能在开发阶段有一定便利，但正式运行中的使用频率低，还会引入敏感硬件数据展示、日志保留、容量、权限、清理和长期兼容成本。

## 决策

不建设常驻的完整 WordPress 在线观测平台。正式环境采用轻量诊断闭环：

1. Agent 负责导出本机硬件反馈 JSON，并展示 HTTP 状态、稳定错误码和简短建议。
2. WordPress 负责返回明确的失败语义，保留业务所需的身份、观测和事件，不长期保存额外调试请求体或命令输出。
3. 日常核对使用最近上传时间、身份归属和变更记录。
4. 疑难故障使用 Agent 证据、完整备份、服务器日志和一次性受控诊断工具处理。
5. 一次性工具不得常驻；使用后必须停用、删除并记录修复前后备份。

## 重新评估条件

只有同时满足以下条件，才重新提出后台诊断面板：

- 同类正式环境故障重复发生；
- 当前最小证据包和服务器日志不足以定位；
- 面板能显著缩短可量化的平均排障时间；
- 已定义最小采集范围、管理员权限、脱敏方式、保留期和自动清理；
- 新增复杂度不会改变插件“简单设备管理”的产品边界。

重新评估必须提交新的 ADR，不通过逐步堆积临时日志形成事实上的观测平台。

## 替代方案

### 完整在线观测面板

优点是集中查看请求和身份计算过程。缺点是低频使用、敏感数据面扩大、运行和维护成本长期存在，因此当前拒绝。

### 完全依赖服务器通用日志

实现成本最低，但无法证明 Agent 实际采集到了什么，也不适合长期记录完整硬件请求。单独使用不足，因此与 Agent 反馈 JSON 组合。

### 仅显示统一的“上传失败”

界面最简单，但会丢失可行动信息，使采集、网络和身份故障混在一起。保留稳定错误码是更小且更有效的方案。

## 后果

- 插件后台保持简单，不增加新的日志表、保留任务和敏感数据页面。
- 排障必须遵循 Agent 与 WordPress 分层证据，而不是只查看一端。
- Agent 错误反馈和服务端错误码属于长期契约，应保持稳定、可复制。
- 复杂故障仍需要工程人员读取备份或服务器日志；这是当前范围下接受的成本。
