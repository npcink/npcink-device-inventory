# ADR-006：旧身份迁移必须校验目标资产的最新硬件证据

## 状态

已接受，2026-08-05。

本决策收紧 ADR-004 的 v1 → v2 过渡查询，不改变 v2 身份类型、哈希算法或新资产创建规则。

## 背景

正式环境中，资产编号 35 曾先用于一台联想笔记本，之后又被行政上复用于一台台式机。台式机 32 与新 35 使用相同型号的华硕主板，但 UUID、主板序列号和永久 PCI MAC 均不同。

历史上传期间，新 35 台式机的一套身份和四条观测被补写到资产 32。后续 Agent 0.3.2 上传时，服务端根据已经存在的 v2 身份正确命中 32，因此表面现象是“35 上传后绑定到 32”，实际原因是数据库中此前已经形成错误归属。

ADR-004 已规定：本次上传的多个 v2 身份分别属于不同资产时返回 409。但当所有 v2 身份尚无拥有者、旧 v1 身份命中一个历史资产时，原实现会直接把全部新 v2 身份补写到该资产，没有比较目标资产最近一次观测中的硬件证据。错误的旧身份关联因此可能被永久固化。

## 决策

旧 v1 身份命中资产后、开始事务和补写 v2 身份前，服务端必须执行迁移一致性检查：

1. 如果目标资产没有最近观测，或最近观测没有可重新计算的 v2 事实，保留原过渡行为。
2. 如果最近观测可以计算出 v2 身份，则它与本次上传必须至少共享一个相同的 v2 身份。
3. 如果两组 v2 身份均非空但完全不相交，返回 `409 legacy_identity_migration_conflict`。
4. 冲突必须在事务开始前失败；不得声明身份、创建观测、更新资产或写入事件。

资产编号、上传备注、使用人、主机名和主板型号不参与该判断。它们是管理信息或弱描述，不能覆盖硬件身份归属。

## 选择理由

### 不直接禁止全部 v1 迁移

真实部署仍可能存在只保存旧身份、尚未完成首次 v2 上传的资产。立即删除过渡查询会产生重复资产，因此继续保留受保护的迁移路径。

### 不要求全部身份完全一致

单次采集可能暂时缺少某个 UUID、主板事实或网卡，设备也可能增加网卡。要求两组身份完全相等会制造不必要的拒绝。至少一个独立 v2 证据相同，才能证明自动迁移有连续性。

### 不用资产编号解决

资产编号可以因行政管理而变更、释放或复用。让上传备注或期望编号参与匹配，会把人为录入错误升级为硬件身份污染。

## 后果

- 旧资产最近硬件与本次上传完全冲突时，系统停止自动迁移并要求人工核对。
- 有共同 UUID、主板序列或永久 PCI MAC 的正常升级仍可自动补写 v2 身份。
- 没有可用历史观测的旧数据仍按原方式迁移；这部分风险通过备份、审计和过渡查询退出计划管理。
- `legacy_identity_migration_conflict` 成为需要排查历史归属、编号复用和身份污染的明确错误。

## 验证标准

- 目标资产无最近观测时，旧 v1 → v2 迁移保持可用。
- 最近观测与上传共享至少一个 v2 身份时，迁移保持可用。
- 两组非空 v2 身份完全不相交时返回 409，且事务没有开始。
- 冲突路径不补写身份、不保存观测、不修改资产。
