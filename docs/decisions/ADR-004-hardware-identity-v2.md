# ADR-004：用独立强信号和永久 PCI MAC 建立硬件身份 v2

## 状态

已接受，2026-08-03。

本决策替代 ADR-003 中“每次上传只写一个 `device_uuid_v1` 或 `fallback_device_v1`”的身份算法；ADR-003 对产品范围、数据模型和服务端计算边界的其他决定继续有效。

## 背景

首次真实环境试点取得了 35、103、133、174 四台 Windows 电脑的只读数据。35、103、174 都有可用系统 UUID 和主板序列号。103 与 174 是相同 Dell Vostro 3690、相同主板型号和 CPU，并返回相同 CPU `ProcessorId`，但系统 UUID、主板序列号和永久 PCI MAC 均不同。133 的系统 UUID与主板序列号是已知占位值，但能取得主板描述、CPU 型号和一块 PCI 物理网卡的永久 MAC。

试点还显示 TPM 信息在四台设备上都不可用，`notUserRemovable` 不能稳定区分板载网卡。旧 `fallback_device_v1` 使用当前 MAC，也没有通过 PNP 总线排除 USB，不能满足“常换部件不影响、可拔插部件不自动合并”的目标。

## 决策

### 1. 独立保存强身份

有效系统 UUID 生成 `system_uuid_v2`；主板厂商、型号和有效序列号生成 `baseboard_serial_v2`。两个事实各自生成身份并同时声明，不再先拼成一个不可拆分的复合主键。

匹配时接受任一已有强身份；如果多个本次身份指向不同资产，则失败关闭并返回 409，不猜测、不自动合并。

### 2. 永久 PCI MAC 只作次级身份

当采集到物理、非虚拟、PNP 总线为 PCI 的网卡永久 MAC 时，结合主板厂商/型号和 CPU 型号生成 `pci_permanent_mac_v2`。每个符合条件的永久 MAC 各生成一个次级身份。

CPU 型号只是组合校验。`ProcessorId`、CPU 序列号、当前 MAC、USB 网卡、硬盘、内存和显卡都不进入摘要。TPM 暂不参与。

### 3. 服务端拥有计算权

Device Agent 可以本地显示相同算法的首个结果，但 WordPress 服务端必须从 schema 5 硬件事实重新计算全部身份。客户端声明的类型和值没有写入权。

### 4. 用一次性 v1 查找避免升级重复

已有内部台账可能只保存 v1 身份。若本次 v2 身份没有拥有者，服务端用同一批事实计算旧 v1 值，仅查找已有资产；匹配成功后在同一事务内为该资产补写 v2 身份。新资产永远只声明 v2。

这是一条有退出条件的过渡路径，不是长期双写兼容层：完成真实环境升级观察后，另行决定删除时间。

## 后果

- 两块同型号主板不会因 CPU 型号或 `ProcessorId` 相同而合并。
- 更换硬盘、内存或显卡不会改变身份。
- 固件事实完整的设备可容忍单个强信号暂时缺失。
- 133 一类固件占位设备可以用永久 PCI MAC 进入自动采集，但更换该网卡会产生新候选，需要人工确认旧资产关系。
- 客户端与插件必须按“先升级插件，再部署 Agent 0.3.0”的顺序更新。

## 验证标准

- PHP 与 Rust 对相同事实生成相同 v2 摘要。
- 相同机型、相同 CPU `ProcessorId`、不同 UUID/主板序列的样本生成不同身份。
- 硬盘、内存、显卡变化不改变身份。
- USB 或只有当前 MAC 的样本不能生成次级身份。
- 多身份指向不同资产时在事务前返回 409。
- 旧 v1 资产首次接收 v2 上传时不创建重复资产，并补写 v2 身份。
- 本地 fixture、Rust 测试、静态检查、发布包和独立 Docker WordPress 演练全部通过后才允许部署。
