# ADR-018：验收不可覆盖的发布候选

## 状态与日期

已接受，2026-10-28。补充 ADR-014 的制品完整性要求。

## 背景

准备 Windows 实机验收时，工作区仍使用已发布的插件3.2.3 / Agent0.4.4，现有ZIP也落后于当前构建。旧tag流程在完成构建后直接公开发布，重跑可覆盖既有资产；preview又不生成更新签名，无法把最终签名制品交给实机验收。

## 决策

- 插件3.2.4 / Agent0.4.5作为当前待验收版本。远端tag构建基于最近正式Release核对两端版本递增和发布范围，已有草稿或正式Release均拒绝覆盖。
- tag构建仅创建draft。随包记录candidate.json（tag、commit、版本、scope及上一正式tag），SHA256SUMS覆盖所有候选文件；下载草稿后核对完整文件集合、哈希及updater签名。
- 原构建另保存90天的独立candidate/校验和证据。公开下载复核必须匹配该成功构建，不能仅相信Release上可被一并替换的校验和；过期候选重新编版构建。
- 操作者核对Windows、插件升级/恢复、上传及安装包证据后，单独人工发布该草稿，不重建或重新上传。发布事件触发独立公开下载复核。候选有改动就使用新版本，不在旧版本下替换字节。
- Windows源码烟测记录明确的作用范围和跳过/手工/可选失败，不能宣称安装、平台签名和更新通过。命令保留stdout/stderr原始字节，使用超时和进程树清理，BAT保留调用者权限。

## 固定更新入口的限制

旧正式Agent0.4.4只读取正式latest入口，不能发现私有draft。因此发布前验证签名、manifest、手动安装升级和配置保留；发布已验草稿后，在指定测试安装补真实官方GUI自动更新，再向工作设备推广。单用户范围允许这两个放行步骤分开记录。隔离更新测试不能冒充旧正式GUI通过。

## 后果

远端流程定义、本地回归、Windows实机、平台签名及公开分发分别记录。当前未配置Windows Authenticode、macOS Developer ID或公证，内部信任环境测试不等于公开外部分发就绪。该机制不自动创建tag、提交、推送或放行；未来执行这些动作仍以具体用户授权和候选证据为准。

工作流程与验收记录模板分别见 [发布说明](../github-release.md) 和 [验收模板](../release-candidate-verification-template.md)。
