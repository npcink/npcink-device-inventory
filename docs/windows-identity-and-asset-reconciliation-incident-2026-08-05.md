# Windows 身份采集与 32/35 资产串号复盘

## 摘要

2026-08-04 至 2026-08-05 的真实设备排障覆盖两类问题：

1. 133 号 Windows 设备明明存在永久 PCI MAC，却持续返回 `missing device identity`。
2. 35 号台式机上传成功后，被系统识别为 32 号资产。

第一类是 Windows PowerShell 5.1 输出编码导致的采集丢失；第二类不是“同型号主板碰撞”，而是历史 v1 迁移把两台机器的身份和观测合并到同一资产。两类问题共同说明：身份故障必须沿“原始事实 → 采集输出 → 规范化身份 → 身份拥有者 → 资产管理编号”逐层定位，不能只看最终错误文案或设备型号。

## 事件一：133 永久 PCI MAC 未进入身份计算

### 现象

Agent 报错：

```text
missing device identity; check system UUID, motherboard serial, or permanent PCI MAC data
```

人工在 PowerShell 中执行物理网卡查询，确认 Realtek PCIe 网卡存在：

```text
PnPDeviceID: PCI\VEN_10EC&DEV_8168...
PermanentAddress: 00E01E84A499
Virtual: false
```

### 第一层误区：命令引用

从 PowerShell 中再次调用 `powershell.exe -Command "...$变量..."` 时，外层 PowerShell 会先展开 `$ErrorActionPreference`、`$_` 和 `$true`，导致命令退化为 `Continue=Stop`、`.Virtual` 等无效文本。

排障时应优先直接在当前 PowerShell 会话逐行执行；若必须嵌套调用，应使用脚本文件或可靠的引用边界，不能把包含 `$` 的双引号命令直接复制进外层 PowerShell。

### 根因

Windows PowerShell 5.1 的重定向输出编码不是稳定的 UTF-8。网卡名称包含中文“以太网”时，Agent 按 UTF-8 解码查询结果失败，并把该次采集当作无可用数据丢弃。因此永久 PCI MAC 虽然由系统返回，却没有进入 JSON 和身份计算。

### 修复

- Windows PowerShell 子进程显式输出无 BOM UTF-8。
- 物理网卡查询先使用 `-IncludeHidden`，失败时退回不带该参数的查询。
- 对 JSON 单对象/数组两种结果统一按数组语义检查。
- 增加中文网卡名称回归测试和 Windows 原生 CI 构建。

相关提交：

- `d5f93e2`：按 JSON 数组检查采集接口。
- `680aad8`：强制 Windows PowerShell UTF-8 输出。

## 事件二：35 台式机被识别为 32

### 关键事实

当前 35 台式机：

- 系统 UUID：`AB35FA0F-349E-C04E-12ED-30C599EEF627`
- 主板：`ASUSTeK COMPUTER INC. / TUF GAMING B760M-PLUS WIFI D4`
- 主板序列号：`260169589201870`
- 永久 PCI MAC：`30:C5:99:EE:F6:27`，另有无线网卡永久 MAC

原 32 台式机：

- 系统 UUID：`B941C172-519E-D865-0D85-B082E20B13BF`
- 同型号主板
- 主板序列号：`260371155600044`
- 历史 MAC：`B0:82:E2:0B:13:BF`

旧 35 资产实际是一台联想笔记本：

- 系统 UUID：`a04029e2-c350-11f0-a4f9-38a7464655f7`
- 设备序列号：`MP2TAV32`

因此同型号主板不是碰撞原因。系统 UUID、主板序列号和永久 PCI MAC 都能区分两台台式机。

### 根因链

1. 资产编号 35 被行政复用，但旧 35 笔记本仍保留该编号。
2. 新 35 台式机早期上传时，v2 身份尚未拥有者，旧 v1 过渡查询命中了资产 32。
3. 原迁移逻辑没有比较资产 32 最近观测中的强硬件事实，直接把新 35 的 v2 身份补写到 32。
4. 此后上传再次命中新 35 已经挂在 32 名下的 v2 身份，因此系统按数据库事实稳定返回 32。

这不是当前匹配器随机出错，而是一次历史错误迁移被新的强身份固化。

## 标准排障顺序

遇到 `missing_identity`、错误绑定或疑似重复资产时，按以下顺序执行：

1. **保存证据**：保留上传错误、硬件反馈、身份探针和服务器完整备份。
2. **确认原始事实**：直接读取系统 UUID、主板厂商/型号/序列、物理 PCI 网卡永久 MAC。
3. **确认采集边界**：检查命令引用、输出编码、单对象/数组 JSON、权限与降级路径。
4. **离线重算身份**：用服务端相同规则判断样本能生成哪些 v2 身份。
5. **查询身份拥有者**：按 `identity_type + identity_value` 查数据库，不根据资产名称、编号或数组下标猜测。
6. **查询观测历史**：比较每条观测的 UUID、主板序列和 MAC，识别一个资产是否混入多台物理机器。
7. **判断匹配阶段**：区分 v2 直接命中、v1 过渡命中、并发声明冲突和新资产创建。
8. **制定修复不变量**：写清哪些资产、身份、观测和 latest 指针应该保留、移动或创建。
9. **先备份、再预检、后事务**：修复必须失败关闭并留下审计记录。
10. **修复后重新导出**：核对资产数量、身份唯一性、观测归属和辅助工具清理结果。

## 工程经验

### 显示编号不是硬件身份

资产编号可以修改，但归档不会自动释放编号，也不能通过“复用编号”改变身份拥有者。编号调整必须先给旧资产重编号，再按需归档，并显式核对新物理设备的身份归属。

### 设备型号只能用于展示和人工筛选

相同型号主板、CPU 或整机非常常见。型号相同不能证明是同一设备，也不能解释身份碰撞。排障结论必须落到规范化 UUID、序列号或永久 PCI MAC。

### 迁移比新算法更危险

新 v2 算法可以严格失败关闭，但兼容旧数据的过渡路径容易绕过这些保证。任何“找到旧记录后补写新主键”的迁移，都必须验证新旧证据连续性，并有明确退出条件。

### 备份必须同时覆盖四表关系

只备份资产表不足以恢复身份事故。至少要同时保留资产、身份、观测和事件；设置可按产品契约选择。修复后必须重新计算或验证 latest observation 等反规范化指针。

### 一次性修复也要像正式代码一样失败安全

临时脚本必须包含固定目标、UUID/指纹白名单、数量断言、事务、回滚、审计和删除步骤。不要在生产数据库中凭记忆执行散落 SQL。

## 防复发措施

- 旧 v1 命中资产时，比较目标最近观测与本次上传重新计算出的 v2 身份；完全不相交则返回 `409 legacy_identity_migration_conflict`。
- 继续保留现有 `identity_evidence_conflict`：本次多个 v2 身份分别属于不同资产时返回 409。
- 资产编号复用前，先给旧资产重编号，再按需要归档，并核对身份归属；归档本身不会释放唯一编号。
- 真实设备排障样本应进入回归 fixture；不得只靠人工复现。
- 完成存量资产 v2 首次上传后，评估删除 v1 过渡查询，减少长期兼容风险。
