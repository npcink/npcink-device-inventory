# 原始采集留档与在线排查开发总结

## 背景与目标

本轮工作解决的是设备采集出现字段缺失、身份异常或上传失败后缺少可追溯证据的问题。目标不是把 Device Agent 扩展成远程运维工具，而是建立一条简单、可解释、可审计的排查链路：

```text
客户端采集 → 本地原始留档 → 签名上传 → 服务端不可变 observation
                                      ↓
                         管理员按需查看、下载和比较
```

实施前，服务端实际上已经在 `raw_json` 中保存完整上传 payload，管理端也能在列表结果中直接展开 raw；桌面端则只能人工导出硬件 JSON，普通上传没有短期本地历史。这说明问题不是“没有原始数据”，而是数据访问边界、解释能力和失败后的本地证据不完整。

## 最终实现

### 服务端与 REST

- observation 列表继续分页，但不再返回完整 `raw`，只返回摘要、标准化硬件和 `rawBytes`。
- 新增管理员专用单条详情：`GET /npcink-device-inventory/v1/observations/{id}`。
- 单条详情返回完整 raw、存储内容 SHA-256、原始字节数、身份判定证据、上一条 observation ID 和字段差异。
- 上一条记录按 `observed_at DESC, id DESC` 的严格前序查找，避免相同采集时间下比较到自身或未来记录。
- 差异采用 JSON Pointer 风格路径，最多返回 200 条，防止异常 payload 造成无界响应。

### 管理端

- 采集列表只展示轻量信息和原始数据大小。
- 点击“查看”后再请求单条详情，避免打开资产详情时一次传输多份大 JSON。
- 详情支持下载原始 JSON、复制 SHA-256、查看系统 UUID/主板序列号/PCI 永久 MAC 证据，以及与上次采集的字段差异。
- 身份结果直接复用 `Npcink_Device_Inventory_Device_Identity_Service`，展示层不维护第二套算法。

### 桌面 Agent

- 每次点击上传后，先采集并把原始数据写入应用私有目录，再发送网络请求。
- 本地文件只包含采集事实、采集器元信息和隐私说明，不包含站点地址、上传配置或授权码。
- 快照最多保留 10 份，并清理超过 30 天的文件。
- 本地落盘失败时终止本次上传，保证一次采集至少留下可排查证据。
- 排障页增加“打开采集历史”，深度排障包仍保持人工生成、人工发送。

## 开发顺序与理由

本轮按以下顺序推进：

1. 先检查 observation 存储、上传契约、身份服务和现有管理端入口，确认 raw 已经持久化。
2. 先收窄列表接口，再增加单条详情，防止新 UI 建立在“大列表携带 raw”的错误契约上。
3. 在详情中增加身份解释和相邻差异，因为两者都依赖完整 raw，适合共享同一次按需请求。
4. 最后实现客户端本地留档，使网络失败和服务端不可达场景也有证据。
5. 补 ADR、长期手册和数据模型，固定新的访问边界和保留策略。

这种顺序体现了一个通用原则：先确定数据所有权和接口边界，再做展示；先保证证据存在，再提高排查体验。

## 关键经验

### 1. 先调查已有事实，不重复造系统

最初需求看起来像“新增原始信息保存”，但代码检查证明服务端已经完整保存 raw。真正缺失的是按需访问、可解释身份、历史比较和客户端失败留档。先查事实避免了新增表、重复上传格式或第二套日志系统。

### 2. 原始事实、标准化结果和排查解释必须分层

- raw 是客户端当时上报的事实，用于追溯和重新解释。
- summary/hardware 是服务端或客户端构造的稳定读取结构，用于日常页面。
- identity decision 和 diff 是按需派生的排查视图，不应反写或覆盖 raw。

三层混合后，解析规则升级会破坏历史证据，也会让列表接口越来越重。

### 3. 列表接口永远不要默认携带大块原始数据

列表应支持搜索、分页和快速浏览；原始 JSON 属于低频详情。采用“轻列表 + 单条详情”可以降低数据库读取、PHP JSON 解码、网络传输和浏览器渲染成本，也使敏感数据权限更清晰。

### 4. 展示判定过程时必须复用真实算法

自审阶段发现，最初的 PCI 永久 MAC 展示规则少检查 CPU 型号，可能出现 UI 显示“有效”而真实身份服务不采用的情况。最终改为调用现有身份服务，再用 raw 组织解释文字。

规范要求：凡是“为什么匹配”“为什么拒绝”的 UI，都必须使用写入路径相同的领域服务结果；不得复制近似判断。

### 5. 本地留档应发生在网络请求之前

如果上传成功后才写本地文件，网络失败时最需要的证据反而不存在。正确顺序是采集、私有落盘、网络上传。落盘失败采用失败关闭，以明确错误代替静默丢证据。

### 6. 常规采集不能借机扩大成深度监控

硬件 observation 与事件日志、进程、dump、驱动信息的隐私风险不同。常规采集可以自动留档和上传；深度排障包必须继续人工触发和人工发送。产品边界比“技术上能采什么”更重要。

### 7. 差异输出必须有限制

递归比较任意 JSON 可能产生巨大结果。当前 ingestion 已限制请求大小、深度和节点数，详情 diff 仍额外限制为 200 条。任何面向排查的派生计算都应有明确的输入和输出上限。

## 后续同类需求规范

### 数据与接口

- raw observation 创建后不可被后续上传覆盖。
- 列表响应不得包含完整 raw；完整 raw 只能从管理员详情接口读取。
- 新增 raw 字段时要检查上传体积、深度、数组数量和字符串长度限制。
- 新增 diff 或分析结果时必须限制最大输出，并明确截断语义。
- 身份、匹配和冲突解释必须复用服务端身份领域服务。

### 客户端文件

- 快照目录使用应用私有数据目录，不写入程序安装目录。
- 文件不得包含上传授权码或完整上传配置。
- Unix 目录权限为 `0700`，文件权限为 `0600`。
- 文件命名包含可排序时间戳，清理时只处理本应用约定前缀和后缀的文件。
- 保留数量、保留天数和失败行为必须有自动化测试或明确验证。

### 管理端体验

- 首屏只加载低成本信息；大 JSON 在明确操作后读取。
- 原始数据、标准化数据、身份解释和历史差异分区展示。
- 下载、复制哈希等操作应保持只读，不产生资产事件或修改事实。
- 第一份 observation 明确显示“没有上次记录”，不能表现为比较失败。

### 安全与隐私

- observation 详情至少要求 `manage_options`，不能复用客户端上传令牌作为读取权限。
- 页面文案应提示 raw 含主机名、UUID、序列号、IP 和 MAC。
- 深度日志、dump 和进程信息不得并入常规自动上传。
- 日志中不得记录上传授权码；文件路径日志只记录必要的文件名或已脱敏路径。
