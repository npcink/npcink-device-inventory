# 分析页组件化收尾复盘与开发规范（2026-08-13）

## 结论

本阶段完成了分析页从“大单体页面”向按业务域拆分的重构，并修复了“资料完整度”区域重复渲染的问题。分析页现在由页面编排层、纯数据层和业务域展示组件组成；用户可见区域遵循单一渲染责任。

## 历史问题归纳

### 已处理的问题

1. 分析能力逐步恢复后，概览、硬件分析、数据健康和资产规划全部堆在一个页面入口中，导致维护和审查困难。
2. 资料完整度的新组件已经包含操作系统分布、问题分组和问题清单，但旧页面 JSX 未及时删除，造成用户端重复显示。
3. 分析类型、硬件盘点聚合、组合查询过滤和共享常量混在页面文件中，修改展示时容易误触数据规则。
4. 硬件盘点需要区分“物理部件数量”和“受影响设备数量”，组合查询需要保持当前筛选上下文和只读详情，这些语义需要稳定的模块边界承载。

### 暂未处理、但有明确原因的问题

- `AnalysisWorkspace` 仍保留跨域查询、状态、导出和事件编排。它是当前的协调层，不再承载各业务域的主要 JSX；继续拆分需要改变状态提升方式，风险和收益暂不成比例。
- 浏览器端聚合尚未改为服务端报表查询。当前资产规模和现有缓存足以支撑交互；只有达到约 1,000 台或出现可测性能回退时才重新评估。
- 最终 WordPress 后台布局仍需人工冒烟验收。静态构建和 Docker 无法完全代替真实浏览器中的响应式、长型号换行和低高度弹窗检查。

## 可复用开发规范

### 1. 先定“谁负责渲染”

新视图开始前先写出唯一渲染所有者。迁移旧 JSX 时，必须在同一变更中删除旧副本，并用 `rg` 检索标题和关键文案确认没有第二份渲染源。

### 2. 数据和展示分层

- 可复用的规范化、聚合、匹配和排序逻辑放入纯函数模块；
- React 组件只消费结果，不复制硬件解析规则；
- 类型、枚举和空查询状态集中管理，避免页面和子组件各自定义一份。

### 3. 口径必须写在界面旁

每个数字注明计数实体：资产、设备、观测或物理部件。缺失值不得默认为零；“未采集”“未填写”“无匹配结果”和“加载失败”保持不同状态。

### 4. 保持只读边界

分析页只根据当前资产和观测派生结果，不新增业务状态，不在分析页直接修改资产。需要处置的动作回到资产管理、设置或事件入口。

### 5. 导出与可见视图一致

CSV 导出必须使用当前视图、分类、筛选和搜索后的数据；新增视图时同时补齐文件名、列口径和空数据行为。

### 6. 按风险分层验证

```bash
git diff --check
npm --prefix vite-admin run lint
npm --prefix vite-admin run check:hardware-audit
npm --prefix vite-admin run build
npm run check:docker
```

UI 变更还需要真实后台冒烟：主导航、子视图切换、筛选、分页、导出、下钻、390px 无横向溢出和低高度弹窗。

### 7. 识别验证副作用

发布或 Docker 验证可能重建 `sj/package-manifest.json`、ZIP 或缓存文件。验证结束后先检查 `git status`，确认这些产物是否属于本次变更；不属于时用补丁恢复，不能把验证副作用混入提交。

## 经验总结

这次问题的根因不是某个 CSS 或条件判断，而是重构时没有建立“旧实现退出、新实现接管”的明确完成条件。今后页面拆分必须把“迁移、删除、唯一性检索、行为验证”视为一个完整工作单元；只要旧代码仍能渲染，就不能把重构视为完成。
