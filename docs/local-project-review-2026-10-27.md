## 新确认并修复的问题

| 优先级 | 问题及触发条件 | 修复与证据 |
| --- | --- | --- |
| P2 | 观测 `find_by_id()` 使用不带版本号的缓存键；事务内读取后回滚，即使调用 `invalidate_cache()`，仍可返回已撤销观测 | ID 查询纳入仓库缓存版本。新增使用实际内存缓存的 fixture，修复前失败；真实 MariaDB 中创建、读取、回滚并失效后查询为 null |
| P1 | 写事务内部提前失效缓存，其他连接在 COMMIT 前把旧快照／旧列表写入新缓存版本；成功提交后仍可能显示旧最新指针、旧观测数和旧事件数。回滚也未覆盖身份／事件缓存 | 上传服务及管理员写控制器在成功 COMMIT 或 ROLLBACK 后，统一失效资产、身份、观测、事件缓存。独立 MariaDB 读连接与写连接共享对象缓存命名空间，在提交前断言读到旧快照，提交后断言最新指针、观测数和事件数立即正确；另有控制器及上传事务 fixture |
| P2 | `claim()` 忽略 `mark_primary()` 的 UPDATE 失败，可将未完成主身份切换的操作报告为成功 | 主身份更新返回布尔结果，失败返回 CLAIM_ERROR，使现有调用方回滚；合法零行更新仍成功。fixture 覆盖失败和幂等更新；MariaDB 注入 UPDATE 错误，接口返回 identity_claim_failed，未新增观测或事件 |

缓存修复保证上述读缓存不会在事务结束后继续沿用；本轮用独立数据库连接和同一缓存命名空间验证竞态，没有部署额外 Redis／Memcached 后端。不改变设备身份算法、归档边界、REST 字段或四张表结构。

| P2 | 恢复预览及导入将资产／身份／观测／事件查重的查询失败当作记录不存在，可能错误规划、跳过关联或重复导入 | 五种查询在错误时立即停止。预览返回结构化错误，实际导入沿用事务回滚。fixture 覆盖预览和仅在事务开始后失败；真实数据库验证后续观测查重失败会撤销之前的资产名称更新 |
| P2 | Linux 桌面端已经将授权码保存在私有配置文件中，但重读时调用无系统凭据存储的平台分支，将其覆盖为空；重启后无法继续使用已保存配置 | 仅在具有系统凭据存储的平台补读授权码；Linux 保留文件值。Linux 上编译真实 `config.rs` 的测试在修复前复现丢失、修复后连续两次读取正常，并检查配置文件 0600／目录 0700 权限 |
