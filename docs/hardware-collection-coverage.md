# 硬件采集覆盖与补齐建议

## 目的

本文记录桌面 Agent 实际采集能力、WordPress 后台消费字段和后续补齐顺序。采集字段用于资产观测；除身份契约明确列出的稳定主机信号外，不参与唯一设备定位。

## 当前覆盖

| 类别 | Windows | macOS | 当前结论 |
| --- | --- | --- | --- |
| 系统、主机名、OS | 已采集 | 已采集 | 可用 |
| CPU 型号、核心数、频率 | 当前频率、最大频率 | 系统支持时采集基准/最低/最高频率 | 可用；不从型号或核心数猜测缺失规格 |
| 内存总量 | 已采集 | 已采集 | 可用 |
| 内存条槽位、厂商、序列号、频率 | 已采集 | 统一内存按单模块表示 | Windows 可用，macOS 符合统一内存语义 |
| 主板、BIOS、系统型号 | 已采集 | 通过 system_profiler 映射 | 可用 |
| 机箱 | 已采集并规范化 | 无独立机箱来源 | Windows 后台字段已对齐 |
| 显卡 | 已采集 | 已采集 | 可用 |
| 显示器型号、厂商、序列号 | 通过 WmiMonitorID 采集 | 部分采集 | Windows 已补齐；转接器、KVM、虚拟显示可能不返回 EDID |
| 显示分辨率、刷新率 | 按 PNP 实例逐屏匹配分辨率；单屏回退刷新率 | 分辨率已采集 | Windows 多屏刷新率仍可能为空 |
| 磁盘容量、文件系统、挂载点 | 保留在原始文件系统数据 | 保留在原始文件系统数据 | 与物理硬盘分层 |
| 物理硬盘型号、序列号、介质、接口 | 已采集 | NVMe/SATA 已采集 | 可用；USB 外置盘取决于系统报告 |
| 网卡、MAC、IP | 已采集；另有物理网卡身份源 | 已采集 | 可用 |
| 默认网关、DNS、DHCP | 已采集 | 已采集 | 使用真实默认路由修正主接口 |
| 电池健康 | 已采集系统可提供字段 | 已采集健康度、循环次数和电量 | 可用；台式机自然为空 |
| 摄像头、声卡、USB 外设 | 未作为静态资产采集 | 未作为静态资产采集 | 按管理需求选择，不建议默认无限扩张 |

## 本阶段补齐

### Windows 显示器

Agent 从 `root\\wmi:WmiMonitorID` 读取 EDID 派生字段，输出到 `graphics.displays`：

- `model`
- `vendor`
- `serial`
- `instanceName`
- `active`
- `yearOfManufacture`
- `weekOfManufacture`
- `currentResX`、`currentResY`、`currentRefreshRate`

WMI 的字符数组会转换为普通字符串。单显示器时，可使用 `Win32_VideoController` 当前模式作为分辨率和刷新率回退；多显示器时不把控制器模式复制到每块屏幕，避免制造错误数据。

显示器关闭、远程桌面、串流软件、KVM、扩展坞或廉价转接器可能隐藏或改写 EDID。此时允许部分字段为空，不能阻断整机上传。

### Windows 机箱

`Win32_SystemEnclosure` 由原始 CIM 大写字段规范化为后台已有读取契约：

- `manufacturer` / `vendor`
- `model` / `type`
- `serial` / `serialNumber`
- `chassisTypes`

## 后续建议

1. **Windows 实机矩阵验证。** 至少覆盖单显示器、双显示器、扩展坞/KVM、笔记本电池、SATA 与 NVMe。
2. **逐显示器刷新率。** 若多屏刷新率确有管理价值，再引入 DisplayConfig API；当前不值得为了一个展示字段增加较重的原生边界。
3. **Storage CIM 增强。** Windows 实机若发现 `Win32_DiskDrive` 对 NVMe 介质类型识别不完整，再用 `MSFT_PhysicalDisk` 交叉补全，而不是替换稳定来源。
4. **按需外设。** 摄像头、声卡、打印机和普通 USB 设备容易产生大量噪声，只有明确盘点需求时再加入。

## 采集边界

- 显示器、显卡、内存、硬盘、网卡更换不应生成一台“新设备”。
- 采集失败应降级为空字段并记录诊断信息，不应阻断其他硬件上传。
- 后台展示字段和 Agent 输出字段必须通过契约测试保持一致。
- 原始平台数据用于排障；后台统计应使用规范化字段，避免把卷、虚拟设备或历史残留重复计数。
