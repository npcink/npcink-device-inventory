# 硬件采集覆盖与补齐建议

## 目的

本文记录桌面 Agent 实际采集能力、WordPress 后台消费字段和后续补齐顺序。采集字段用于资产观测；除身份契约明确列出的稳定主机信号外，不参与唯一设备定位。

## 当前覆盖

当前工作区采用完整硬件采集：本地检查、JSON 导出和普通上传共用同一路径，快照标记为 `npcink-hardware-inventory-v3`，不复用旧轻量快照。上传 observation 仍为 schema 5；新增字段属于硬件事实扩展，不改变身份算法。安装包发布及 Windows 实机验收尚未执行。

规范化字段用于分类和汇总，平台来源字段保留在 `platformData`，查询状态随 `collection` 上传。“详细信息”按部件展示全部收到的字段，未知字段保留原名，`0` 与 `false` 不被隐藏。完整实施说明见 [完整硬件采集与展示](complete-hardware-inventory-2026-10-27.md)。

## 本阶段补齐

### Windows 显示器

Agent 从 `root\\wmi:WmiMonitorID` 读取 EDID 派生字段，输出到 `graphics.displays`：

- `model`
- `vendor`
- `serial`
- `instanceName`
- `active`
- `yearOfManufacture`
- `weekOfManufacture`
- `currentResX`、`currentResY`、`currentRefreshRate`

WMI 的字符数组会转换为普通字符串。单显示器时，可使用 `Win32_VideoController` 当前模式作为分辨率和刷新率回退；多显示器时不把控制器模式复制到每块屏幕，避免制造错误数据。

显示器关闭、远程桌面、串流软件、KVM、扩展坞或廉价转接器可能隐藏或改写 EDID。此时允许部分字段为空，不能阻断整机上传。

### Windows 机箱

`Win32_SystemEnclosure` 由原始 CIM 大写字段规范化为后台已有读取契约：

- `manufacturer` / `vendor`
- `model` / `type`
- `serial` / `serialNumber`
- `chassisTypes`

## 后续建议

1. **Windows 实机矩阵验证。** 至少覆盖单显示器、双显示器、扩展坞/KVM、笔记本电池、SATA 与 NVMe。
2. **逐显示器刷新率。** 若多屏刷新率确有管理价值，再引入 DisplayConfig API；当前不值得为了一个展示字段增加较重的原生边界。
3. **存储对应关系。** 当前已保留 Get-PhysicalDisk 和可靠性计数器的返回值；后续实机核对设备编号与物理盘/卷的对应关系，不按容量猜测。
4. **来源局限。** 驱动不报告的显存、SMART 寿命、多屏刷新率等不能补造，后续通过真实样本选择更可靠来源。

## 采集边界

- 显示器、显卡、内存、硬盘、网卡更换不应生成一台“新设备”。
- 采集失败应降级为空字段并记录诊断信息，不应阻断其他硬件上传。
- 后台展示字段和 Agent 输出字段必须通过契约测试保持一致。
- 原始平台数据用于排障；后台统计应使用规范化字段，避免把卷、虚拟设备或历史残留重复计数。


## 前序修复记录（完整采集实施前）

下文记录本日早期轻量路径修复与当时验证，当前规则以上方完整采集说明及实施文档为准。

资产详情恢复原有概览卡片，内存只展示已知总容量，主硬盘展示摘要；逐条内存和逐块硬盘的规格放在“详细信息”标签页。内存明细包含容量、类型、厂商、料号、频率、插槽和序列号，不据此推断双通道。界面读取当前上传结构 `hardware.memory.modules`，修正此前只按 `hardware.memory` 数组取值、遗漏已有事实的问题；相同读取规则用于硬件摘要、导出及没有总量字段时的分析容量计算。

安装容量以部件容量之和展示；仅有操作系统总量或采集器占位记录时仍显示已知容量，但明确提示条数、品牌、型号和频率未采集。统一内存不显示为“一根内存条”；厂商十六进制代码原样标注为代码，不猜测品牌。

硬盘按记录展示型号、容量、介质、厂商和接口。当前物理磁盘与历史文件系统记录分别标注为硬盘、卷；仅有挂载点/文件系统且没有物理型号、序列或接口证据的记录，不用于宣称物理磁盘数量。缺失字段显示“未采集”，不把 C/D 分区当作两块磁盘。

截图对应的资产 186 在 2026-10-21 的观测使用 Agent 0.4.4 / `npcink-upload-light-v3`，`hardware.memory.modules` 为空，硬盘只有三个文件系统卷，缺失确实来自普通上传路径。普通上传此前未查询 `Win32_PhysicalMemory` 和 `Win32_DiskDrive`，本次将两项查询移入与完整采集共用的 Windows 基础采集函数，避免重复查询。配置频率为 0 时回退到有效的标称频率；容量为 0 的空插槽不计为内存条。查询失败保留其他采集结果和诊断状态，不阻断上传。

此改动不改写历史观测、不影响身份算法。缺失字段需使用更新后的 Agent 重新采集并上传，刷新页面不能补出旧记录缺少的信息。Windows 实机采集、安装、签名更新及远端 CI 按用户安排留待后续。

验证：修复前新增普通上传回归因缺少内存条明细失败，修复后采集库 38 项、桌面库 14 项测试及两侧 Clippy 通过；覆盖双内存、频率回退、物理硬盘、查询失败和旧缓存拒绝。`npm run check:hardware-audit --prefix vite-admin` 覆盖嵌套内存、空插槽、统一内存、物理盘/卷区分，以及“详细信息”实际字段输出；lint、TypeScript/生产构建、打包规则及体积预算通过。本地浏览器打开现有资产 186，确认概览恢复为卡片、内存展示 64 GB，“详细信息 → 内存”仅展示旧观测已有总量。未向 device.local 写入演示资产。
