# 设备身份、采集与发布阶段复盘

## 阶段结果

截至 2026-08-05，项目完成了从“能上传硬件”到“身份、编号、观测和发布边界可解释”的一次完整收口：

- 35、103、133、174 已能由当前 Agent 正常上传并匹配。
- 133 的中文网卡采集问题定位为 Windows PowerShell 5.1 输出编码，而非 WordPress 接口或单机硬件故障。
- 32/35 串号问题定位为旧 v1 → v2 迁移缺少最新硬件证据连续性保护。
- 旧 153 与 `E2E260805073327495` 的案例明确了“同一设备可以有两条历史资产，但编号不能替代身份判断”。
- 资产编号冲突从通用数据库 500 改为稳定的 `409 duplicate_number`，活动与归档资产使用同一唯一规则。
- Windows/macOS 补齐显示器、机箱、物理硬盘、真实默认路由、DNS、DHCP、CPU 静态规格和电池健康等高价值观测。
- WordPress 插件 3.1.2 和 Agent 0.3.3 已发布；生产站插件已升级并保持启用。

## 关键问题与真正根因

### 1. 133 为什么采集不到可靠身份

最初现象是 133 无法像其他 Windows 设备一样形成稳定身份。直接检查硬件反馈后发现，系统 UUID 和主板序列号属于厂商占位值，只能依赖符合约束的 PCI 永久 MAC。Agent 已执行正确的 PowerShell 查询，但中文接口名通过本地代码页输出，Rust 按 UTF-8 解码失败，整段物理网卡 JSON 被丢弃。

经验：看到“字段缺失”时，必须依次检查命令是否执行、输出编码、JSON 单对象/数组形态、规范化和上传映射，不能直接把问题归因于硬件或后端。

### 2. 为什么新 35 曾匹配到资产 32

新算法本身没有把两台机器算成同一身份。错误发生在历史兼容阶段：v2 无拥有者时，旧 v1 命中资产 32，系统直接把新 v2 身份补写过去，没有比较资产 32 最近观测与本次上传是否共享硬件证据。错误一旦写入，后续 v2 直接命中只是在延续已经污染的归属。

经验：兼容迁移比新算法更危险。任何“旧键命中后补写新键”的流程，都必须验证证据连续性、事务边界和失败前无副作用，并定义退出条件。

### 3. 为什么把新记录改成 153 会报 500

旧 153 虽已移除或归档，但数据库仍保留该编号的唯一占用。后端没有先做业务冲突检查，数据库写入失败后统一包装成 `asset_update_failed / 500`。这既隐藏真实原因，也诱导用户重复操作。

经验：数据库约束是最后防线，不是用户错误语义。可预见的唯一冲突应先返回业务 409，同时保留重复键并发兜底。

### 4. 为什么 135 等设备没有显示器

Windows Agent 只采集了 `Win32_VideoController`，输出 `graphics.controllers`；后台读取的是 `graphics.displays`。因此这是系统性契约缺口，不是 135 单机问题。补齐时使用 WMI EDID 和 PNP 实例；多显示器无法可靠对应刷新率时保持为空，避免复制显卡控制器模式制造错误事实。

经验：排查“后台没显示”必须同时核对采集源、Agent JSON、上传 observation 和后台消费路径。字段名和层级不一致与“系统采不到”是两类问题。

## 形成的工程规范

### 事实分层

| 层级 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| 资产 | 编号、名称、使用人、部门、状态、财务字段 | 自动判断物理设备 |
| 身份 | 服务端计算的稳定硬件证据及唯一归属 | 展示编号、主机名、可更换部件 |
| 观测 | 某一时点的 CPU、内存、硬盘、显示器、网络、电池等事实 | 永久设备主键 |
| 事件 | 创建、修改、上传、迁移和人工修复审计 | 当前硬件详情 |

任何需求先判断属于哪一层。无法明确归层时先停下来补契约，不通过增加一个“万能 UUID/metadata”字段规避设计。

### 身份与编号操作

1. 先根据资产 UUID 查询身份拥有者和最近观测，不根据显示编号猜测。
2. 同一物理设备产生旧新两条资产时，保存备份并写清应保留的资产、身份、观测和编号。
3. 复用编号前先给旧资产重编号，再归档；归档本身不释放编号。
4. 身份迁移至少共享一个独立 v2 证据；完全不相交返回 409。
5. 自动合并、自动转移编号和自动覆盖观测均不作为默认能力。

### 采集实现

1. 优先使用操作系统自带、只读且可降级的接口，避免为低价值字段引入重依赖。
2. 每个平台先保留原始来源，再输出后台契约使用的规范化字段。
3. 物理设备与逻辑资源分开：物理盘不等于卷，显示器不等于显卡控制器，物理网卡不等于当前路由接口。
4. 单对象/数组、空值、占位值、字符串数字、字符数组和中文编码必须有 fixture。
5. 采集失败不能阻断整机上传；身份必需事实不足则由服务端按契约返回 422/409。
6. 显示器、硬盘、内存、显卡、电池等信息不得进入身份摘要。

### 排障闭环

1. 记录稳定错误码、HTTP 状态和操作时间。
2. 导出 Agent 硬件反馈，不先猜 WordPress 数据库。
3. 对照 Agent 原始 JSON、规范化 observation、服务端重算身份和数据库拥有者。
4. 数据修复前后分别做完整备份；固定目标、数量和指纹断言，并在事务中执行。
5. 一次性诊断工具使用后删除，不建设低频、常驻、保存敏感请求体的在线观测平台。

### 发布闭环

1. 插件和 Agent 分别使用独立版本，但必须通过统一版本契约。
2. 先升级 WordPress 插件，再部署新 Agent，确保服务端理解新事实和错误语义。
3. 本地必须通过 fixture、PHPStan、PHPCS、前端构建、Rust fmt/Clippy/tests 和依赖审计。
4. 最终 ZIP 必须经过结构检查、WordPress.org 规则、Docker 干净安装、官方 Plugin Check 和真实备份恢复演练。
5. tag 工作流完成后核对 Windows/macOS 安装包、签名、`latest.json`、`latest-desktop.json` 和公开下载地址。
6. 生产后台上传后检查版本、启用状态、管理页面和浏览器控制台。

## 控制复杂度的原则

- 优先补齐阻塞资产管理的事实：身份、编号冲突、物理硬盘、显示器、默认网络、电池；摄像头、声卡、普通 USB 等低价值噪声按需再做。
- 只为重复出现且现有证据不足的问题增加长期诊断能力。
- 通过明确错误码、反馈 JSON 和规范化文档提高可排障性，不用常驻大面板代替契约。
- 多来源无法可靠映射时留空比猜值更正确。
- 新功能必须说明不做什么、失败行为、数据归属和删除/退出条件。

## 当前基线与下一步

- WordPress 插件：3.1.2，生产站已升级。
- Device Agent：0.3.3，Windows/macOS 安装包和更新清单已发布。
- 35、103、133、174 可继续使用当前 Agent 上传。
- 下一步在 135 安装 Agent 0.3.3，验证单/双显示器、物理硬盘、默认网络和（如适用）电池；将真实差异补成 fixture，而不是立即改变身份或数据模型。
- 存量资产完成至少一次 v2 上传后，单独评估 v1 过渡查询的删除条件。
