# 设备上传排障与运行规范

## 目的

本文是 Device Agent 与 WordPress 插件在正式运行阶段的最小排障手册。它把 35、103、133、174 的实机验证，以及 133 采集失败和 32/35 历史串号事故中得到的经验，整理成稳定的职责边界、证据清单和处理顺序。

完整事故事实见 [`windows-identity-and-asset-reconciliation-incident-2026-08-05.md`](windows-identity-and-asset-reconciliation-incident-2026-08-05.md)；身份算法与错误语义见 [`identity-contract.md`](identity-contract.md)。

## 系统职责边界

```text
Device Agent
  读取本机硬件事实
  → 规范化采集结果
  → 形成并上传 JSON

WordPress 插件
  验证请求与权限
  → 根据硬件事实重新计算身份
  → 定位或创建资产
  → 检查冲突并事务化保存观测
```

Agent 不是单纯的文件传输器。它负责操作系统命令、输出编码、权限、JSON 单对象/数组差异和网络请求。WordPress 是资产归属的最终裁决者；它不信任客户端传入的身份哈希，也不会用资产编号、主机名、使用人或备注决定设备身份。

## 唯一设备定位规则

自动匹配只使用服务端从上传事实重算出的强身份：

1. 有效系统 UUID；
2. 有效主板序列号；
3. 物理、非虚拟、PCI 网卡的永久 MAC。

一台设备可以同时拥有多条身份。任意身份已经属于不同资产时，上传失败关闭，不自动合并。旧 v1 身份只用于存量资产首次升级定位；命中后若目标资产最近观测与本次上传的 v2 证据完全不相交，返回 `409 legacy_identity_migration_conflict`，不写入任何数据。

资产编号只是管理字段，可以修改，但不能通过复用编号改变身份拥有者。复用编号前必须先重编号或归档旧资产，并核对资产 UUID、身份和观测归属。

## 最小证据包

遇到上传失败或错误定位时，先保存以下证据，再修改配置或数据：

- Agent 导出的硬件反馈 JSON；
- 上传时间、Agent 版本、目标站点和设备备注；
- HTTP 状态、稳定错误码和服务端返回信息；
- WordPress 完整备份，至少覆盖资产、身份、观测和事件；
- 必要时直接读取的系统 UUID、主板序列号和物理 PCI 网卡永久 MAC。

不要只保存截图或最终错误文案。硬件反馈说明 Agent 实际采集到了什么，服务端返回说明请求在哪个边界被接受或拒绝，两者缺一不可。

## 标准排障顺序

1. **确认版本**：核对 WordPress 插件与 Agent 是否为预期版本，先排除旧客户端或旧插件。
2. **确认原始硬件事实**：直接读取 UUID、主板序列和永久 PCI MAC，不用型号、当前 MAC 或 CPU `ProcessorId` 猜测。
3. **确认 Agent 采集结果**：检查反馈 JSON 是否包含上述事实；缺失时查权限、PowerShell 编码、命令兼容和 JSON 形态。
4. **确认传输边界**：检查站点地址、授权、签名、网络和 HTTP 响应。
5. **确认服务端身份计算**：离线或在测试环境用同一规则重算 v2 身份。
6. **查询身份拥有者**：按 `identity_type + identity_value` 查找，不按显示编号或数组下标判断。
7. **核对观测历史**：检查一个资产是否混入多台物理机器，并验证 `latest_observation_id`。
8. **安全修复**：完整备份、固定目标预检、单事务修改、失败回滚、写审计记录、修复后重新备份。
9. **实机复验**：由原设备重新上传，确认返回资产编号、身份拥有者和观测数量均符合预期。

## 错误码分流

| 现象或错误 | 优先排查 | 处理原则 |
| --- | --- | --- |
| Agent 本地采集缺字段或解析失败 | Agent | 检查系统命令、编码、权限和 JSON 结构 |
| 网络、授权、签名或 HTTP 请求失败 | Agent 与接口边界 | 保留原始状态码和响应，不把网络错误解释成身份错误 |
| `missing_identity` | Agent 采集事实 | 确认三类强身份是否至少有一类可用 |
| `identity_evidence_conflict` | WordPress 身份拥有者 | 多条强身份已属于不同资产；禁止自动合并 |
| `legacy_identity_migration_conflict` | WordPress 历史资产与观测 | 检查编号复用、旧 v1 关联和历史身份污染 |
| 上传成功但返回错误资产 | WordPress 数据关系 | 立即停止批量上传，备份并核对身份、观测和 latest 指针 |

## 运行阶段的诊断策略

正式环境不建设完整的在线观测平台。低频疑难故障不足以证明长期保存请求体、命令输出和调试日志的收益高于其复杂度与敏感数据风险。

默认保留以下轻量能力：

- Agent 可导出硬件反馈 JSON；
- 上传失败展示 HTTP 状态、稳定错误码和简短建议；
- WordPress 返回可区分的错误码并保留必要的观测与事件；
- 设备详情继续以最近上传时间、身份和变更记录支持日常核对；
- 需要深度排障时使用证据包、完整备份、服务器日志和一次性受控工具。

只有当同类故障在正式环境重复发生、现有证据无法定位，并且能定义数据最小化、权限、保留期和清理规则时，才重新评估后台诊断面板。决策见 [`ADR-007`](decisions/ADR-007-keep-production-diagnostics-lightweight.md)。

## 已验证基线

截至 2026-08-05：

- WordPress 插件 3.1.1 已部署并通过官方 Plugin Check；
- Device Agent 0.3.2 已修复 Windows 物理网卡查询重试、JSON 数组处理和 PowerShell UTF-8 输出；
- 35 已正确定位到资产 35；
- 133 可通过 PCI 永久 MAC 形成身份；
- 103、174 上传正常；
- 3.1.1 已阻止缺乏硬件证据连续性的旧 v1 → v2 自动迁移。

这组设备证明当前路径可用，但不是删除 v1 过渡逻辑的充分条件。删除前仍需确认全部存量资产已经至少成功完成一次 v2 上传。
